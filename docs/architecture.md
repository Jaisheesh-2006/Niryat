# Architecture

The [product plan](PLAN.md) owns scope. Through Phase 6, Niryat implements sign-in, profiles, health/export checks, clients, invoice PDFs, approved sandbox invoicing/refunds/reminders, ledger ingestion, dispute polling, tasks, FIRA matching, source-quoted extraction, monthly close, GSTR-1 preview/CSV, advance-tax estimates, a compliance calendar and an AI-assisted dashboard. Phase 6 local acceptance is user-confirmed (2026-11-01), except the blocked CSV-import check; sponsor licence coverage remains unverified. FIRA parsing remains verified only against a synthetic fixture. Hosting and reliability remain Phase 7; see [verification](verification.md).

## Components and flow

```mermaid
flowchart LR
  Web[Next.js web] --> API[Hono API]
  Hooks[PayPal webhooks] --> API
  API --> DB[(Postgres / Drizzle)]
  API --> Rules[Pure rules package]
  API --> Close[Close orchestrator]
  Worker[Render Workflows] --> Close
  Cron[Monthly cron] --> Worker
  Close --> Claude[Claude read and draft tools]
  Claude --> Reads[Scoped PayPal Toolkit reads]
  Close --> Queue[Proposed actions]
  User[User approval] --> Runner[Approval runner]
  Queue --> Runner
  Runner --> PayPal[REST and Server SDK writes]
  API --> Files[Document storage]
```

Verified PayPal events and transaction backfill populate the ledger. Issuing an invoice creates a PDF and persistent proposal; user approval permits PayPal execution. Refund/dispute records feed cited messages, tasks and reports. Uploaded FIRA PDFs are parsed and matched without AI; uncertain matches require confirmation. Claude investigates/drafts and configures dashboard widgets; it does not compute compliance figures.

## Sign-in

Sign-in uses the existing sandbox app's authorization-code flow and server-side userinfo. A unique payer ID identifies returning users; an email collision does not link accounts, and no login token is retained. PayPal-only users have a nullable password hash (migration `0004_closed_mantis`). Both sign-in methods use the existing signed session cookie. The app owner uses email sign-in; seller operations still use that app owner's credentials. In local development the web proxy targets `API_URL=http://localhost:3001`, while browser links and the callback use `PUBLIC_APP_URL`.

Freelancers use `/login` and `/signup`; chartered accountants use `/ca/login` and `/ca/signup`, without PayPal login. Each signup endpoint fixes its account role. Password login checks credentials before returning a wrong-portal response; PayPal sign-in excludes CA accounts. Signed role-aware sessions enforce API access: CAs cannot use freelancer routes. The web layouts verify `/auth/me`; `src/proxy.ts` uses the unsigned cookie role only to route people between `/overview` and `/ca`.

B3 adds freelancer share requests under Profile → Your CA and CA responses at `/ca/requests`. `ca_links` permits one pending or accepted link per freelancer; creation stores a normalized email without checking for a recipient account or sending mail. Signup emails are unverified. A 256-bit private invitation code, shown only on creation and stored only as SHA-256, supplies the additional proof: the freelancer hands it to their intended CA, who redeems it through JSON `POST /ca/requests/claim` using the invited email. That atomic hash/email/status check binds the pending link to the CA user id before any requester details or accept/decline controls are available. Codes never appear in URLs, GET responses or logs; lost codes require cancelling and recreating the invitation.

Accept/decline requires that claimed CA and email; ending sharing requires its owner or accepted CA plus the exact displayed `linkId` in the JSON body. Status-checked atomic updates cannot reopen ended links or let an old end request affect a replacement link. `/ca-link` returns only the owner's active link. Migration `0009` ends all unproved pre-fix active shares (history retained; administrative `ended_by` null) and requires an invitation hash for new active links. Users must re-invite after upgrading. These requests alone grant no access to compliance records or PayPal actions; CA record reads and client pages remain B4/B5.

## Three-layer PayPal integration

A5 judge mode (2026-11-05) is explicitly enabled by `JUDGE_MODE=true`; otherwise `/auth/judge` is unavailable and `/judge-mode` reports false. The auth-rate-limited JSON endpoint starts the existing signed role session only for the fixed demo account with the matching role, no password and no PayPal payer ID. The public flag contains only a boolean, disables caching and is false without database/auth configuration. A shared client component checks the flag after hydration on home and both login pages, then uses fresh role navigation after login.

`pnpm seed:judge` composes rules in `apps/api/src/seed-judge.ts` and persists through `packages/db/src/seed-judge.ts`. It validates inherited configuration without loading private environment files. One transaction/advisory lock makes initial/repeated/concurrent seeding atomic; a reserved-account collision rolls it back. Three freelancer ledgers and one CA are created with null credentials, encrypted profiles/client addresses, synthetic history/FIRA lines and hash-proven accepted invitations through the existing claim/accept helpers. No PayPal call or approval action is created. Unpaid fixtures have null PayPal invoice IDs; synthetic judge payments are blocked by their reserved transaction prefix in refund proposals and execution. Reruns preserve records/edits and original seed dates, including ended sharing. Use a fresh disposable demo database for a later fresh countdown. Shared-account/privacy, operator setup and pending browser checks are in [A5](IMPROVEMENTS.md#a5-judge-mode-seed-and-try-as-judge-p0).

| Layer                 | Owner                    | Responsibility                                       |
| --------------------- | ------------------------ | ---------------------------------------------------- |
| TypeScript Server SDK | packages/paypal/src/sdk  | Transaction search and refunds                       |
| PayPal Agent Toolkit  | packages/agent           | Five projected, owner-scoped read-only agent tools   |
| Typed REST client     | packages/paypal/src/rest | Invoicing v2 and Disputes v1, absent from Server SDK |

Webhook verification belongs to packages/paypal/src/webhooks and uses PayPal's verify API before ingestion. The Server SDK supplies capture/refund reads, approved refunds and paginated transaction search through the ledger adapter. The REST client implements Invoicing and Disputes with cached OAuth tokens, POST request IDs, validation and action-specific retries. Reminders explicitly disable retries because endpoint idempotency is unverified ([ADR 0004](decisions/0004-reminders-via-rest.md)). Toolkit reads are implemented; Toolkit writes remain deferred. See [PayPal guide](paypal.md).

## Corrections and proof

Refund notifications, approved refunds and reconciliation converge on `recordRefundById`: read the completed refund, ensure its capture is recorded, link it to an invoice and persist a positive refund row with PayPal's fee/net fields. Invoice-refund notifications first read the current invoice's PayPal refund IDs through REST. An unlinked refund stays in the ledger without a user task. One SQL roll-up computes invoice payment/refund status; `creditNoteFor` and `realisationFor` supply the compliance view. A lost dispute alone never subtracts money.

Dispute webhooks and the sync's seven-day Disputes API poll converge on `recordDispute`. It ensures the first disputed capture, preserves invoice links and ignores stale PayPal updates. Only linked disputes create user tasks. `ensureTask` deduplicates refund/opened-dispute/lost-dispute tasks by stable keys; only the user marks them done. Invoice and task reads are owner-scoped. Local `pnpm dev` does not schedule reconciliation: `sync:payments --no-agent` reconciles without Claude. The scheduled CLI records deployment-wide `sync_runs` (migration `0010`); a partial unique index skips overlapping polls before ledger reads. Success means both payment and dispute reconciliation finished with zero failures, independently of later nightly reminders. `GET /sync-status` exposes only freshness metadata to signed-in freelancers; Today and invoices show relative update time, a two-hour stale warning and the latest failure. This is the polling timestamp, not a monthly close's `asOf`, individual webhook time or guarantee that PayPal has indexed an event. Direct monthly-close reconciliation and explicit refund recovery do not update this timestamp.

A killed sync process can leave its running row behind. After confirming the poll process has stopped, an operator must mark that row failed before another poll can start; no time-only lock expiry risks overlapping a still-active poll. See [Render E1 recovery steps](RENDER.md#e1-sync-freshness-and-light-reconciliation).

E1 overlap correction (2026-11-05): the nightly and light crons can both start at 20:30 UTC. A busy light poll still skips immediately; the nightly CLI retries the existing lock ten times with 5/10/20/30-second capped backoff (245 seconds total). Once acquired, it performs its own reconciliation before running reminders once. Each retry and the reminder phase use the current time, including after an IST midnight rollover. A lock still busy after the retry budget produces an explicit error and nonzero exit, without touching another poll's row or running reminders against the in-progress poll. Schedules and the killed-poll recovery policy are unchanged; see [review fix checks](RENDER.md#e1-review-fix-nightly-reminders-on-poll-overlap).

FIRA upload requires a session, `application/pdf`, explicit storage consent and at most 2 MB. The API checks PDF bytes, extracts text with `unpdf`, validates the deterministic parser's output and rejects unreadable documents before storage. SHA-256 detects duplicates per user. Matching accepts an exact reference/amount/currency match at full confidence; amount/date suggestions wait for confirmation. A payment is reserved only once. The database saves the document, source lines and matches atomically; invoice status is matched, pending or missing based on payment matches and covered months. See [spec 07](specs/07-fira-matching.md) for the synthetic-layout limitation and demo seed.

## Approval and trust boundaries

Every PayPal write requires explicit user approval. Issuing saves an immutable invoice/PDF and proposed `agent_actions` payload without calling PayPal. The authenticated approve route checks ownership, then the runner atomically claims a proposed or failed invoice/refund action before execution. Created PayPal IDs survive retries with stable `<actionId>-<step>` request IDs. Reminders can claim only `proposed`, permit one attempt and cannot resend after failure or interruption; unknown outcomes also cannot be rejected as unsent. Success finishes as done; rejection is final. Webhook verification/reconciliation are deterministic ingestion paths. The in-product agent may use only scoped, logged Toolkit reads without approval ([ADR 0005](decisions/0005-agent-boundary.md)); it has no write or approval tools.

Zod validates external inputs and environment values. Rules are pure, versioned and cited; AI handles extraction, investigation, explanations and widget configuration, never legal or numeric truth. FIRA matching remains deterministic. All twelve YAML `logic` entries now name implemented functions; none remains `TODO`.

## Agents, close and extraction

The close orchestrator first syncs payments/disputes, loads owner-scoped invoice views, ensures overdue tasks, builds SQL month totals and FIRA status, and selects rule-due reminder candidates. Claude then investigates with Niryat reads and five Toolkit wrappers (`get_invoice`, `list_invoices`, `get_dispute`, `list_disputes`, `list_transactions`) before drafting advice, tasks and a focus summary. Code validates known entities, digit-free narrative and proposal stages, then persists immutable proposed actions and deduplicated tasks. Every due candidate gets a standard-reminder proposal even when Claude is missing, fails, exhausts its budget or skips a candidate; those proposals carry `agent: null`. Rejected stage keys remain reserved. An older pending stage is not replaced when the next stage arrives.

`agent_runs` stores user, kind, trigger, month, `asOf`, status, structured summary and estimated AI cost. One running row per user/kind is allowed; a later start can fail a row stale after 15 minutes. `agent_tool_calls` stores sequential system/agent inputs, outputs and outcomes. Toolkit response logs contain item/byte summaries, not raw PayPal bodies. Projections drop PayPal personal fields and filter known ownership before Claude sees data. Model text is advisory; deterministic figures and citations remain available after AI failure.

The SDK has no built-in tools, filesystem settings or persisted sessions, and sees only Niryat's supplied MCP server. Its minimal subprocess environment excludes PayPal, storage and database credentials. Bare `allowedTools` can bypass the redundant `canUseTool` callback; validation/dispatch wrappers and absence of execution tools enforce the actual boundary. A deployment-wide monthly cost estimate, turn bounds and per-run caps constrain AI use. Concurrent/in-flight costs can overshoot the monthly cap by a run; this is not a provider billing guarantee.

`POST /close` reserves a current-IST-month manual run before dispatch, returns HTTP 202 and keeps concurrent starts at 409. With `RENDER_API_KEY` or `RENDER_USE_LOCAL_DEV=true`, the API dispatches `niryat-worker/monthlyClose` with the owner, month, `asOf`, manual trigger and reserved run ID, using that ID as the SDK idempotency key. Without dispatch configuration it retains in-process local execution. The page refreshes every three seconds while running. A dispatch error is ambiguous: it returns a sanitized 503 without local fallback or releasing the reservation, because Render may already have accepted it. A run older than 15 minutes becomes failed/stale on the next start, as before.

The worker validates the shared task input and runs only the specified freelancer when `userId` is supplied; CAs are rejected. For reserved manual runs it locks and checks the exact owner/dates/trigger/running status and age, then claims the unique first audit slot (`workflow_claim`). Duplicate, stale, completed or replaced deliveries skip execution. A worker crash after claim does not replay that run; use a new user-initiated close after stale recovery. The original `asOf` survives a midnight rollover. Proposal/task deduplication and the one-attempt rule for approved PayPal reminders stay intact: recovery never resets a claimed reminder.

`close:run` and the unscoped Workflows task run scheduled closes over freelancers sequentially, defaulting to the previous IST month. The CLI accepts `--month` and `--as-of` directly, without an extra `--` separator. Demo `asOf` affects rule dates and real dedupe keys; it does not rewind PayPal data or the run timestamp. The nightly sync runs only the reminder agent when new candidates exist. E2 automated tests simulate API replacement and duplicate delivery; actual hosted dispatch and restart recovery remain Phase 7 user checks.

Extraction sends the brief once to a separate Claude draft tool. Code checks each field against its verbatim quote, including full amount/email tokens and negative signs, before showing it. Logs retain found field names and run/cost metadata, not the brief. `Use these values` only prefills forms; existing-client matching is explicit, export answers and SAC stay with the user, and Discard saves no client, invoice or action. Form submission issues the invoice, and user approval separately permits its PayPal send. Missing/budget-exhausted AI leaves manual forms available.

## Reports, calendar and dashboard

`GET /gstr1` supplies `/gstr1` with rules-derived periods/due dates, LUT coverage and per-currency invoice/refund/net reconciliation. `POST /gstr1/file` emits the ten-column WOPAY CSV with user-entered per-invoice INR rates and applicable GST percentages. Refund credit-note data is listed separately for Table 9B. GST registration and filing frequency gate the report. Offline-tool parser acceptance remains blocked before import.

`GET /advance-tax` supplies the server-rendered GET form at `/advance-tax`. Invoice-linked payments/refunds are selected by IST receipt date in the tax year; rates are supplied per currency. Rules determine presumptive eligibility/deemed income and instalment dates/amounts from the user's estimated tax. No income-tax liability or slabs are computed. Rates remain request-only in both report flows.

`GET /calendar` supplies `/calendar` with rule/profile/invoice/dispute events. Bryntum Calendar/React 7.3.8 runs client-only in read-only agenda/week/month/year/list modes, defaulting to month with day disabled. GST, income-tax, RBI and PayPal resources supply category colours from light/dark CSS tokens and the built-in sidebar filter; state title prefixes and classes remain. The year view is January–December (user-approved C1 limit), so April–March spans two year pages. Unresolved overdue RBI/dispute events remain visible beyond the historical display window; other past events and future events retain their existing window. Each event carries a per-kind action and a rules-derived source (null for disputes/expected recurring invoices). Hover tooltips use text nodes and a guarded local Open link; the server-rendered list links every overdue event and the next ten upcoming ones with their actions. Recurring dates remain expectations because series cycles are unlinked. See the [C1 change record and pending browser checks](BRYUNTUM.md#c1-category-resources-filter-sidebar-and-views).

`GET /ca/calendar` requires a CA session and builds events only for accepted clients via `listCaClients`, prefixing IDs with the freelancer ID and rewriting links to the read-only CA client page. Its projected zod contract contains client IDs/names and events with `freelancerId`. `/ca/calendar` reuses the same client-only, read-only Bryntum views and tooltips, using clients as resource colours/sidebar choices and local category checkboxes as a second filter. Static sidebar configuration retains its identity across category rerenders, preserving user collapse state. The existing four CSS tokens cycle by client index; names identify clients when colours repeat. Its server-rendered all-overdue/next-ten-upcoming table includes client names and actions. Ended links disappear on the next request; delivered pages remain snapshots. See the [C3 change record and pending browser checks](BRYUNTUM.md#c3-ca-multi-client-calendar).

`GET /dashboard` projects owner-scoped ledger/health rows without client email/address fields or health-flag citations. AG Studio/React 3.0.0 renders the seven required widget groups with Niryat theme tokens; refunds and disputes use separate tiles. Display sums may use floating point; compliance figures come from rules/PayPal records. Missing PayPal FX remains missing, and bank FX loss is not computed. Edit mode exposes the AI Assistant and layout controls.

AG Studio's Agent Framework uses a browser adapter to `POST /dashboard/turn`. The API validates the bounded text/tool wire subset, session, deployment-wide budget and per-user concurrency, records a charged `dashboard` run and calls the server-only Claude Messages adapter. Tools execute in the dashboard; no PayPal tools are exposed. Digit-containing model prose becomes a figure note; arguments remain intact. Logs keep tool names/argument keys and sanitized status codes, never prompts, argument values, model text or keys. Replies are buffered and replayed as AG events, not server-streamed. Client names and projected ledger data go to Anthropic. Thinking blocks remain unsupported; model-compatibility guidance preceded successful user question checks. See [V16](verification.md#v16-phase-6-acceptance).

B6 (2026-11-05) adds `/ca` as a distinct AG Studio portfolio dashboard with five widgets and the B5 server-rendered client table. `GET /ca/dashboard` and `/ca/portfolio` share accepted-client loading in `apps/api/src/ca-dashboard.ts`; deterministic per-user projections are tagged with freelancer ID/name and omit customer contact details, action/PDF payloads and health citations. The portfolio retains B5 identity fields, but Studio sources exclude emails. Charts group by freelancer ID and currency; current financial year comes from rules, not browser date arithmetic. The assistant infers portfolio scope from the CA's signed role, rejects query parameters, records a dashboard run under the CA user ID and applies the same budget/concurrency/logging and IP/user rate limit as freelancer turns. It grants no compliance or PayPal write capability. Revocation excludes a client from subsequent reads; already loaded dashboards remain snapshots until reload. See [B6 checks and limits](IMPROVEMENTS.md#b6-ca-portfolio-ag-studio-dashboard-p1-ag-studio-prize).

`AG_STUDIO_LICENSE_KEY` is read by the web server and passed to the browser by design; absent keys use trial behavior. Bryntum uses the trial alias and needs no licence key; the trial covers judging. AG Studio trial dates remain open in [V15](verification.md#v15-sponsor-licences).

## Storage and runtime

The web app's `lib/glossary.ts` supplies plain explanations and responsibility labels. `Term.tsx` renders visible text before an accessible abbreviation without JavaScript; native disclosures collect explanations on busy record/calendar pages. D1/D2 reuse it across freelancer, CA and public pages. Rules remain the sole source of legal calculations; revised wording retains citations, PDF/CSV/PayPal text contracts and user approval.

apps/web uses Next.js App Router; apps/api uses Hono on Node 24. Shared packages export TypeScript source; their build step checks types, while Next produces production assets. apps/worker registers the `monthlyClose` task with Render's SDK and a 900-second timeout, validates input and calls the shared close composition root.

The web app proxies /api/* to the API through Next rewrites, so the session cookie stays same-origin.

Rate limits ignore `X-Forwarded-For`. The API trusts validated `CF-Connecting-IP` only when Render's server environment sets `RENDER=true`; elsewhere, or without a valid header, it uses the connection address. [Render's public ingress overwrites that header](https://render.com/articles/host-pocketbase-on-render#making-pocketbase-see-the-real-client-ip). The Blueprint binds web's `API_INTERNAL_HOSTPORT` to the API's private-network `hostport`; both the rewrite and server-side reads prefer it over `API_URL`, keeping the original ingress header across the web-to-API hop. Same-workspace private services are trusted. The API remains public for existing direct URLs and webhooks. A public web-to-API hop would replace the header with the web service's IP and combine users' limits, so keep this hop private. Limits are in-memory per API instance and reset on restart; AI/share keys also include the verified session user ID. Hosted proxy behavior remains awaiting user verification.

Web route groups preserve public URLs: `(public)` contains home, login, signup and disclaimer; `(app)` contains `/overview` (Today) and the signed-in pages. The app layout validates `/auth/me` with the shared session schema before rendering the account email and shell. Its single `nav-menu` aside is the desktop sidebar and the mobile native popover; only that nav renders the reminder-proposal count. Root `app/error.tsx` catches app-layout failures with `retry`; app loading and independent overview card boundaries provide partial feedback. Sponsor imports remain route-scoped, outside the shell import graph. `lib/format.ts` supplies display-only IST dates and decimal-string money formatting; compliance calculations remain in rules.

Drizzle declares sixteen tables, including CA links and E1's sync runs. Migration `0005` adds runs/tool calls; `0006` adds nullable profile `gstr1_frequency` and `specified_profession` and permits the `dashboard` run kind; `0010` adds polling history. Migrations live in packages/db/drizzle; createDb in packages/db/src/client.ts; GSTIN, PAN fragments and profile/client addresses are AES-GCM encrypted. Invoice PDFs use private S3-compatible storage (local SeaweedFS in development). The API streams them through `/files/:token`, exposed by the web proxy as `/api/files/:token`; the PDF link is included in the PayPal invoice note. FIRA PDFs use the same private store under `fira/<userId>/<documentId>.pdf`, with no public token or link; source text is stored in plaintext in Postgres. `seed:fira-demo` creates a demo ledger only for an account with no invoices. See [local storage](local-storage.md) for setup and its development-only encryption limitation.

The Render Blueprint defines two web services, a workflow service, paid Postgres and three crons. `niryat-sync-light` runs every half hour (`*/30 * * * *` UTC) with `sync:payments --no-agent`, targeting 30-minute freshness without Claude configuration or execution. `niryat-sync` retains seven-day reconciliation and nightly reminders at `30 20 * * *` UTC (02:00 IST). `niryat-monthly-close` runs at `30 1 1 * *` UTC (07:00 IST on the first), dispatching `niryat-worker/monthlyClose` with the SDK; the task itself has no schedule. Local P5-13 acceptance used the API CLI fallback, not Workflows dev. Hosted task registration, all crons, webhook delivery, measured sync freshness and restart recovery remain [Phase 7 checks](build-flow.md#phase-7-judge-mode-hosting-and-freeze-nov-58).
