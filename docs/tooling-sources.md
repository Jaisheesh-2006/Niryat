### Invoicing v2 reminders

[PayPal's reminder reference](https://developer.paypal.com/api/invoicing/v2/invoices-remind) specifies **`POST /v2/invoicing/invoices/{invoice_id}/remind`**, with optional top-level `subject`, `note`, `send_to_invoicer` (default false), `send_to_recipient` (default true) and `additional_recipients`. These are the notification body fields, not a nested `notification` property. `subject` and `note` allow up to 4000 characters; additional recipients must already belong to the invoice's CC list. Success is **204 with no response body**. The reference limits reminders to two per day.

**User decision (2026-10-30): standard reminders.** The current reference says custom `subject` and `note` values are replaced by PayPal's system wording. Niryat will send only `{ send_to_invoicer: false, send_to_recipient: true }` after the user's approval. Claude investigates and gives send/hold advice with a reason inside Niryat; it does not generate reminder email text. No reminder templates, wording selector, deterministic email tail or separate email service are needed. The approval button will say `Send PayPal's standard reminder`; success will say `Reminder request accepted by PayPal.`

The local `current-phase-plan.md` carries the matching payload, draft-tool, summary/log, test and UI contracts for P5-3/P5-5/P5-6/P5-8/P5-10/P5-12. P5-13 will record the decision in ADR 0004 and the user's delivery evidence in V03. HTTP 204 establishes request acceptance; notification/email receipt and wording must be observed separately or recorded as unverified. No reminder was sent to test delivery, and this documentation change does not implement the later tasks.

**Retry requirement:** reminder endpoint support for `PayPal-Request-Id` is unverified. P5-5 must opt this POST out of both transport retries and 401 refresh-and-resend, and restrict its persistent approval claim to `proposed` only. All failed/interrupted reminder attempts remain blocked from resending, even across restart; unknown outcomes cannot be rejected as unsent. Other action types retain their retry behavior. Add a regression using the real client with fake fetch: remote acceptance followed by a lost response produces exactly one POST, and subsequent approval cannot send again. This conservative rule can leave a reminder unsent after a crash/rejection; no new status, migration or recovery flow is needed. [PayPal's idempotency reference](https://developer.paypal.com/api/rest/reference/idempotency/) warns that header support is API-specific.

Context7 `/paypal/agent-toolkit` supplied [API dispatch](https://github.com/paypal/agent-toolkit/blob/main/typescript/src/shared/api.ts), [parameters](https://github.com/paypal/agent-toolkit/blob/main/typescript/src/shared/parameters.ts) and [usage](https://github.com/paypal/agent-toolkit/blob/main/typescript/README.md). Current-main examples are not version guarantees. Exact **1.11.0** `package.json`, `openai/index.d.ts`, `openai/index.js` and `mcp/index.d.ts` establish:
- Public exports are **`/mcp`, `/ai-sdk`, `/openai`, `/bedrock`, `/langchain`**; there is no root or `/shared/api` export.
- **Client-credential dispatcher:** import `{ PayPalAgentToolkit }` from **`@paypal/agent-toolkit/openai`**. Construct it with `{ clientId, clientSecret, configuration: { actions, context: { sandbox: true } } }`. Its public **`handleToolCall({ id, type: "function", function: { name, arguments: JSON.stringify(args) } })`** calls the internal runner directly and returns a tool-message object whose **`content` is the runner's JSON string**. It needs no OpenAI client or model request. OpenAI types are supplied by the package's ordinary `openai` dependency; no extra framework peer installation is needed.
- **Direct runner export:** `{ PayPalAPI }` is public from **`@paypal/agent-toolkit/mcp`**. `new PayPalAPI(accessToken, { sandbox: true }).run(name, args)` returns `Promise<string>`. This entry takes an existing token; its client class is not exported for client-credential construction. The `/openai` dispatcher above fits D24 without adding token acquisition. `/mcp`'s MCP SDK is also an ordinary dependency, not a missing peer.
- Configuration filters tool discovery, **not execution**: `handleToolCall` dispatches the supplied name even if it was absent from `getTools()`. Keep the wrapper's name allowlist and zod validation before dispatch. The dispatcher JSON-decodes arguments but does not run the tool parameter schema.
- Parsed runner failures can be **`{ ok: false, status?, code, message }`** for `LlmError`, or **`{ error: { message, type: "paypal_error" } }`** for other throws. Reject both, as well as invalid JSON; never log their raw messages.
