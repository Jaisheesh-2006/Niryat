## Devpost draft

### Inspiration and problem

Indian freelancers paid from abroad must connect invoices, PayPal fees, refunds, disputes and payment proof to their export records. Those records often live in separate screens and spreadsheets. Niryat brings them together for the freelancer and their chartered accountant (CA).

### Who it is for and what it does

Niryat helps Indian service-export freelancers using PayPal and the CAs reviewing their work. It drafts invoices from emails, checks export details, records payments and adjustments, matches payment proof, prepares monthly summaries and GSTR-1 export data, and shows upcoming work. A freelancer can share records with one CA; the CA sees only accepted clients and cannot send or approve PayPal actions.

### How PayPal and Claude are used

PayPal connects invoice delivery, payments, refunds and disputes to the export records. Approved invoice sends and reminders use Invoicing REST APIs. The Server SDK reads captures/refunds and reconciles transaction history; approved refunds use the same SDK. Disputes REST reads and signature-verified webhooks feed the ledger. PayPal supplies the payment, fee and net figures.

The Claude Agent SDK extracts source-quoted invoice drafts and investigates the monthly close. Five allowlisted PayPal Agent Toolkit reads are scoped to the freelancer's known records and logged. Claude drafts advice and tasks; it has no PayPal write or approval tools. The freelancer separately approves each PayPal action. Pure, cited rules supply compliance calculations and deadlines. Missing or exhausted AI leaves manual forms and deterministic reminder proposals available.

### Sponsor tools and implementation

AG Studio powers two themed dashboards: a freelancer ledger dashboard and a CA portfolio across accepted clients. Both expose an AI Assistant in edit mode, through a server-only Claude proxy. Bryntum supplies read-only compliance and multi-client calendars, category/client filters and action tooltips with rule sources where available. Render configuration defines monthly-close Workflows, durable manual-close dispatch, half-hour reconciliation without AI, nightly reconciliation with reminders and paid Postgres. Hosted execution remains to be verified. APIMatic's PayPal Context Plugin informed the Server SDK implementation; the [usage log](apimatic-usage.md) links that guidance to shipped code.

The application uses Next.js, Hono, PostgreSQL/Drizzle, validated boundaries and an approval queue. Financial records are scoped by owner or accepted CA share. The demo offers shared, synthetic freelancer and CA accounts; newly approved sandbox invoices can demonstrate actual PayPal delivery separately.

### Business model

**Free for freelancers; CA firms pay per client.** This is the intended business model; billing is not implemented.

### What we learned

An agent needs narrow tools and visible evidence. Niryat separates investigation from execution, retains tool-call outcomes and keeps numeric decisions in rules. PayPal reconciliation complements webhooks; reminder retries need special care because an uncertain send must not be replayed automatically.

### Limitations and verification status

- Sandbox only. No real money moves. Each deployment uses one PayPal seller; connecting each freelancer's own seller account is future work.
- Seeded history and FIRA payment-proof samples are synthetic. Real PayPal India FIRA layouts remain unverified. Shared judge accounts are mutable; never enter personal data. Seed reruns preserve edits and original LUT dates.
- Rules cite primary sources but have not been reviewed by a CA. This is not tax or legal advice, and nothing is filed automatically.
- Invoice PDFs are not digitally signed and do not convert foreign amounts to INR. GSTR-1 CSV import acceptance is blocked before validation in the offline tool; it is not an import pass.
- Hosted webhooks, measured polling freshness, Workflows dispatch/restart recovery and the five-scene demo are awaiting user verification. New CA sharing/role isolation, view-only controls, synthetic-refund guards and new dashboard/calendar interactions also await their user checks. Existing local acceptance does not establish hosted behavior.
- AG Studio licence coverage through 2026-12-15 and the December AI budget are awaiting operator confirmation. Bryntum coverage past that date is user-confirmed in V15. The AI cap uses stored cost estimates and is not a hard provider-billing guarantee.
- Refund raw-webhook/HTTP evidence and automatic dispute-webhook delivery remain open. Claude's hold advice is advisory; a prior simulated-date run used an imprecise “payment today” explanation. Do not treat that as proof of payment in progress.

These are the current limits; update only from actual user evidence in [verification](verification.md), [Phase 7](build-flow.md#phase-7-judge-mode-hosting-and-freeze-nov-58) and [IMPROVEMENTS](IMPROVEMENTS.md) before copying to Devpost. ## Recording and rehearsal (user only)

### Start and prepare

1. For local rehearsal use Node 24 and pinned pnpm: `corepack pnpm install --frozen-lockfile`, then `corepack pnpm --filter @niryat/api dev` and `corepack pnpm --filter @niryat/web dev` in separate terminals. On restricted PowerShell replace `corepack` with `corepack.cmd`. API health: `http://localhost:3001/health` → `{"status":"ok"}`; web: `http://localhost:3000`. For final recording use the eventual hosted web URL instead; hosting is outside F1.
2. Privately configure the database, encryption/session keys, sandbox PayPal seller, storage for PDFs, and Claude model/key/budget using the [setup guide](../README.md#environment). For PayPal login use the [matching HTTPS callback procedure](paypal.md#log-in-with-paypal). Never capture keys, passwords or private account details.
3. For initial setup on a dedicated demo database, apply `corepack pnpm db:migrate`; with inherited `JUDGE_MODE=true` and private `JUDGE_BUYER_EMAIL`, run `corepack pnpm seed:judge`. Start or restart the API with `JUDGE_MODE=true` too; expect `/judge-mode` on the API origin to return `true` and both demo buttons to appear after hydration. If the original synthetic LUT has expired before a later rehearsal, refresh its dates through Profile using [H3](IMPROVEMENTS.md#h3-keep-alive-to-dec-15-and-refresh-demo-dates-p0-phase-8-user). Preserve the database and invoice-number history; seed reruns do not renew it. See [A5](IMPROVEMENTS.md#a5-judge-mode-seed-and-try-as-judge-p0).
4. Open a separate buyer browser session using the sandbox buyer credentials supplied privately by the owner. Keep the seller/freelancer and CA sessions separate too. The judge seed supplies dashboard history and accepted CA links, but **no reminder candidates**. Synthetic payments cannot be refunded, and synthetic history must not be presented as PayPal transactions.
5. For scene 3, prepare real, sent, unpaid sandbox invoices in Niryat under the recording freelancer: one reminder-eligible invoice for a client with an actual open dispute on another paid invoice, and one safe reminder-eligible invoice for a different client. Do not pay the reminder invoices in scene 2. Use rule-derived dates/stages, not invented legal intervals. The [V03 procedure and evidence](verification.md#v03-invoicing-and-reminders) documents simulated-date `close:run --month YYYY-MM --as-of YYYY-MM-DD` through `corepack pnpm --filter @niryat/api close:run`; it affects real stage dedupe keys and all freelancer accounts, so use it only in an isolated rehearsal deployment. Label any simulated date on screen. A current UI close does not offer an `asOf` override. Do not alter seed records or promise Claude will choose a particular tool or hold reason.
